## 2. New findings

### N3-M1 (medium, probable): a tag run whose commit later reaches `main` through a merge commit is still promotable

- Location: `eng/deploy/site_artifact.py:116-133` (`_check_on_branch`), `.github/workflows/deploy-production.yml` summary line "Commit is on main: yes".
- What happens: the fix proves that the run's commit is an **ancestor** of `main` today and that no tag `main` exists **today**. It does not prove that the run was started by a push to the branch `main`. A commit can become an ancestor of `main` long after its run.
- Attack path (an agent with Contents write, prompt-injected or with a stolen token, and no tag ruleset in place): on branch `x`, commit C1 changes `deploy-test.yml` to run on `push` of tags, drop `environment`/`id-token`, and upload a malicious `wwwroot` as `site-sha256-<its digest>`. Push tag `main` at C1: the run is `deploy-test.yml`, event `push`, `head_branch` `main`, success. Delete the tag. Commit C2 reverts the workflow file. Open a pull request `x` → `main` whose net diff is harmless and does not touch `.github/workflows/` (CODEOWNERS works on the net diff). If it is merged **with a merge commit**, C1 becomes an ancestor of `main`: `compare(C1...main)` is `ahead`, no tag exists, every check passes, and the approver is told "Commit is on main: yes". Squash and rebase merges create new SHAs, so C1 never reaches `main` that way.
- Preconditions: agents can create tags (README now asks for a tag ruleset that forbids it), merge commits are allowed on `main`, and someone promotes that run id. Each is a setting, hence medium, not high.
- Minimal fix, settings: the tag ruleset (README step 4), plus "Require linear history" on `main` (or allow only squash and rebase merges). Code (pick one): require that the run deployed to environment `test` (`GET /repos/{r}/deployments?environment=test&sha={head_sha}` with a `success` status whose `log_url` names this run id; the environment's branch rule of type Branch `main` is enforced by GitHub, and a tag run is refused there or has no deployment), or require that `head_sha` is on the first-parent chain of `main`. Add the case to `site_artifact_tests.py`.

### N3-L1 (low, confirmed): the licence record is checked for presence, not for the owner's decision

- Location: `tests/secure/ThoughtTree.Architecture.Rules/Deployment/DeployToolRules.cs:66-96`; `eng/deploy/licences.json:10-90, 92-104`; `eng/deploy/deploy-client.json:2`.
- What happens: (a) a package passes when it is recorded with the same licence string, whatever its `status`; all 16 entries say "awaiting owner approval", including `spawn-command` and `valid-url` with no licence field (ADR-050: unknown licences only with human approval). An agent can add any new package with any licence by adding an entry with status "awaiting". (b) For the binary, the rule only checks that some key starts with `StaticSitesClient@`; it does not compare the build id with `deploy-client.json`, does not record or compare the SHA-256, and does not check `status`. The approval's condition "a new pin needs a new decision" is therefore not enforced: a pull request that changes `deploy-client.json` to another build passes every rule. `eng/deploy/` is owner-reviewed (CODEOWNERS), which limits this to a missed review.
- Minimal fix: fail unless `status` is `approved` (or `rejected` packages are absent from the lock); key the binary as `StaticSitesClient@<buildId>` with its `sha256`, and assert both equal `deploy-client.json` and `status` is approved. Update the stale comment in `deploy-client.json` ("needs the owner's approval"). Merge condition: the owner decides the 16 pending entries first.

### N3-L2 (low, confirmed): seven checks of `site_artifact.py` can be removed without a test failing

- Location: `site_artifact.py:89-90, 128`, `:173, 181, 189, 196, 199-201, 216`; `site_artifact_tests.py` (`FakeGitHub` replaces `_api` and `urlopen` entirely; artifacts in fixtures have no `digest` field).
- Surviving mutants: zip digest check removed (`:200`), `size_in_bytes` limit removed (`:181`), download size cap removed (`:196`), `expired` filter removed (`:173`), `https://` redirect check removed (`:189`), `_api` returning `{}` instead of failing on an HTTP error (`:90`), and the 40-hex check of the run and branch SHAs removed (`:128`). The "more data than its header states" check (`:216`) also survives, but `zipfile` itself stops at the declared size, so that one is defence in depth. Today all these checks are correct by reading; the gap is that nothing keeps them so, which was N-M1's point.
- Minimal fix: add tests with an artifact `digest` that differs from the zip, a `size_in_bytes` over the limit, a stream longer than the cap, an expired artifact, an `http://` location, and a test of the real `_api` with a stub opener that raises `HTTPError` (expect `SystemExit`) and returns a 302 for `raw=True`.

### Info

- N3-I1 (confirmed): **what the `@file` change protects.** It removes the OIDC JWT from argv. It does not keep the job's processes from the credential: `ACTIONS_ID_TOKEN_REQUEST_TOKEN`/`_URL` stay in the environment of every step of the deploy job (fetch, `install-tools.sh`, `apply-infra.sh`), readable in `/proc/<pid>/environ` by any process of the same user, which can request its own token. Azure CLI also persists the assertion: `client_assertion` goes to `~/.azure/service_principal_entries` (azure-cli-core `auth/identity.py`), which lives until `upload-site.sh` removes `~/.azure`. The real control is that no untrusted code runs in the deploy jobs, which the build/deploy split now gives. The script's comment ("where every process of the job could read it") overstates the gain; no change needed beyond wording.
- N3-I2 (confirmed): `deploy-test.yml:95` puts `GH_TOKEN` (`contents: read`, `actions: read`) at job level, so it now reaches the Azure CLI, Bicep and the sign-in in `deploy-test` too (as already in production). `upload-site.sh` removes it before the deploy tools. Narrower: set it only on the fetch step.
- N3-I3 (confirmed): the rule for the test deploy job's fetch (`PromotionRules.cs:63`) checks `--same-run` and `--expect-sha256` but not `--branch main`, `--workflow` or `--event push`; dropping them passes. Impact limited to the test site (the `test` environment allows only `main`). `SecretOnCommandLine` does not match the `--federated-token=$token` form.
- N3-I4 (probable): `actions/upload-artifact` v4 and later skip hidden files unless `include-hidden-files: true`, while `digest` hashes them. A dotfile in `wwwroot` would make every test deployment fail (fail-closed, availability only).
- N3-I5 (confirmed): `apply-infra.sh` compiles Bicep after the sign-in with the Bicep binary the runner image or Azure CLI supplies; its version is not pinned by the repository. Same trust as the Azure CLI itself; recorded for completeness.
- N3-I6 (confirmed): **the `--same-run` mode cannot be used against another run**: it requires `--run-id` equal to `GITHUB_RUN_ID` and `--expect-sha256`, and still checks path, event, repositories, branch and the N-H1 checks; a production run that passed `--same-run` would fail the `path` check (its own run is `deploy-production.yml`).
