## 2. New findings

### N-H1 (high, probable): a tag named `main` passes the "deploy-test run on main" check, so a run that never ran on `main` can be promoted to production

- Location: `eng/deploy/site_artifact.py:90-106` (`_check_run`: `head_branch == branch`), used by `deploy-production.yml:151-154` and `:191-195`; `infra/README.md:33` ("checks ... that the run is a successful push run of `deploy-test.yml` on `main`").
- What happens: the check compares `head_branch`, `event`, `path`, `conclusion` and the repositories. For a run started by pushing a **tag**, the GitHub API reports the tag name in `head_branch` and `event` is `push`. The workflow file path is the same whatever its content. Nothing checks that `head_sha` is a commit of `main`.
- Attack path: an agent (Contents write; prompt-injected or with a stolen token) pushes a commit on any branch in which `.github/workflows/deploy-test.yml` is changed to run on `push` of tags, drops `environment` and `id-token` (no Azure needed), and uploads a malicious `wwwroot` (CSP removed, exfiltrating script) as `site-sha256-<its digest>`. It then pushes a tag `main` at that commit (git allows a tag and a branch of the same name). The run is listed under `deploy-test` with the label `main`, succeeds, and writes the same "Promotable build" summary. The agent then asks, in a pull request or issue, for that run id to be promoted, or waits for the owner to pick the newest `deploy-test` run. `verify` passes every check; the approver sees a commit id and a digest, which is what a genuine run shows too. After approval, production serves the attacker's files. No CODEOWNERS path is touched, because the changed workflow never reaches `main`. The approval is the only barrier, and it was told the run is from `main`.
- Why probable: `head_branch` carrying the tag name for tag-triggered runs is documented GitHub behaviour and is widely reported, but was not tried here. If a tag ruleset already stops agents from creating tags, this is closed by the settings.
- Minimal fix: in `_check_run`, when `--branch` is given, also require that `head_sha` is in the branch: `GET /repos/{repo}/compare/{head_sha}...{branch}` returns `status` `ahead` or `identical` (the branch contains the commit). Also fail if `GET /repos/{repo}/git/matching-refs/tags/{branch}` returns any ref. Add a ruleset that restricts tag creation to the owner. Show `head_branch`, `event` and "commit is on main: yes" in the `verify` summary. Add a rule test that `fetch --branch` is followed by the ancestry check (or a unit test of `_check_run` with a recorded tag run).

### N-M1 (medium, confirmed): the artifact checks in `site_artifact.py` have no tests

- Location: `eng/deploy/site_artifact.py:90-106, 115-137, 140-201, 204-220`; no test project or rule exercises them (`grep site_artifact tests/` finds only string checks in `PromotionRules.cs:279-284`).
- What happens: the only defence between attacker-controlled preview artifacts and the deploy job with the preview identity is this script: entry name checks (`..`, absolute, backslash, colon, control characters, duplicates), link rejection, size limits, the zip digest, `_check_run`'s repository and event checks, and `preview_target`'s PR checks. A later change that drops one of these checks (for example the `..` test, or the head-repository comparison) passes every test in the branch check. The reviewer ran `_safe_entries` against crafted archives (traversal `a/../../x`, absolute path, symlink entry with mode `0o120777`, newline in the name, case-folded duplicate): all were rejected, and a name with shell metacharacters (`y z;$(id).js`) was accepted, which is fine because no name reaches a shell. So the code is correct today, but nothing keeps it so.
- Minimal fix: a Secure test (Python `unittest` run from the branch check, or a C# test that runs `python3 -I` on fixture archives) with the cases above plus zip bomb (declared size smaller than data), more than `MAX_FILES` entries, missing `index.html`, digest mismatch, and `_check_run` fed recorded API answers (fork head repository, wrong path, wrong event, tag run from N-H1).

### N-M2 (medium, confirmed): the rule tests still pass for workflow changes that break the pull request isolation

- Location: `tests/secure/ThoughtTree.Architecture.Rules/Deployment/PullRequestIsolationRules.cs:15, 43-54, 100-116`.
- Changes that violate the intent and pass:
  1. In a `workflow_run` workflow, `run: git fetch origin "$HEAD_SHA" && git checkout FETCH_HEAD && eng/deploy/publish-client.sh ...` (or `gh run download` and running a file from the artifact): the rule looks only at `actions/checkout` with `ref`/`repository`.
  2. Removing `github.event.workflow_run.head_repository.full_name == github.repository` from `preview-deploy.yml:94`: no rule asserts any fork filter (the Python check still holds, but it is untested, N-M1).
  3. `PullRequestEvents` omits `merge_group` (runs queued pull request code before merge) and `push` on non-`main` branches; a job on these triggers with `id-token: write` passes. Its token subject (`ref:refs/heads/...`) matches no federated credential today, so Azure stays closed, but the rule's stated guarantee is wider than what it checks.
  4. Reusable workflows are followed one level only, and not at all when called from another repository.
  5. `Only_deploy_test_reaches_the_test_site...` matches literal strings (`rg-thoughttree-test`), so `"rg-thoughttree-""test"` or a variable passes.
- Minimal fix: for every job of a `workflow_run` workflow, reject any `run` that contains `git fetch`, `git checkout`, `git switch`, `gh pr checkout`, `gh run download` or `download-artifact` followed by execution, and require that artifact download goes through `site_artifact.py fetch`; assert the `head_repository` condition on every `workflow_run` job that has `id-token: write`; add `merge_group` to `PullRequestEvents` and add a rule that every job with `id-token: write` has an `environment`; follow reusable workflows recursively and forbid remote ones in jobs with `id-token`.

### N-L1 (low, confirmed): `deploy-test` builds in the same job that holds the test identity

- Location: `.github/workflows/deploy-test.yml:30-95` (one job: `id-token: write`, `environment: test`, then `publish-client.sh` runs `dotnet publish` at `:55`).
- What happens: `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN` are in the environment of every step of the job. `dotnet publish` runs MSBuild targets, analyzers and source generators of every NuGet package in the lock files. A malicious package version merged through a lock-file update (or a process that outlives the build step) can request the OIDC token and act as the test identity: read the test site's deployment token and overwrite the test site, or read the argv token of N-L3. Impact is the test site only, and the same build output goes to production anyway, so a compromised build already compromises production after approval; this finding is about the credential being reachable, which architecture.md line 347 rules out.
- Minimal fix: split `deploy-test` like production: job `build` (no `id-token`, no environment) publishes and uploads the artifact; job `deploy` (`environment: test`) fetches it with `site_artifact.py fetch` and uploads. This also makes test and production run the identical deploy path.

### N-L2 (low, confirmed): dependencies with licences outside the ADR-050 list are not approved on record

- Location: `eng/deploy/package-lock.json` (license fields), `eng/deploy/deploy-client.json:2`, `infra/README.md:41`.
- What the lock says: 306 MIT, 31 ISC, 12 BSD-3, 5 BSD-2, 5 Apache-2.0; and outside the list: `BlueOak-1.0.0` (5), `0BSD` (3), `CC0-1.0` (1), `(MIT OR CC0-1.0)` (3), `(MIT OR WTFPL)` (`expand-template`), `(BSD-3-Clause OR GPL-2.0)` (`node-forge`), and **no licence field** for `spawn-command` and `valid-url`. ADR-050 needs a human approval for "similar permissive" and forbids unknown licences without approval. `StaticSitesClient` (closed source, Microsoft terms) is flagged in the README as needing approval but no approval is recorded. The licence check of ADR-050's verify line is still not implemented (`push-gate.yml` summary), and none of the new rules checks npm licences. YamlDotNet 18.1.0 is MIT, as the comment in `Directory.Packages.props` says (from NuGet metadata; not re-checked here).
- Telemetry (ADR-030): `NO_UPDATE_NOTIFIER=1` is set, `AZURE_CORE_COLLECT_TELEMETRY=false` in the deploy workflows; StaticSitesClient's own network behaviour is unknown (not covered).
- Minimal fix: record the owner's approval (licences above, `StaticSitesClient`) in the pull request or as an ADR-050 note; check the licences of `spawn-command` and `valid-url` in their repositories; add a rule that fails on a lock entry whose licence is not on an allow list.

### N-L3 (low, confirmed): previews deploy any open pull request of the repository without review and serve its own configuration

- Location: `preview-deploy.yml:88-141`; `infra/README.md:39`.
- The `preview` environment has no required reviewer (README step 2 adds none), so every pull request from a branch of this repository gets its own content and its own `staticwebapp.config.json` (no CSP, any redirect, any route) on a public `*.azurestaticapps.net` address. `check-headers.sh` then fails the run, but the preview stays online until the pull request closes. The origin is separate (Public Suffix List, I6 of the first review), so it reaches no test or production data. Risk: a phishing or malware page under the project's preview site, created by a prompt-injected agent, and the Free plan's three slots used up (availability). Accepted in the README, recorded here so the owner decides it knowingly.
- Minimal fix (if wanted): delete the preview when `check-headers.sh` fails (`az staticwebapp environment delete` in a `trap`), or require a reviewer on the `preview` environment for pull requests not authored by `ProductOwnerRole`.

### N-L4 (low, probable): `Microsoft.Web/staticSites/write` lets a pipeline identity change the site's plan and settings outside the template

- Location: `infra/bootstrap/bootstrap.bicep:72`.
- `staticSites/write` covers the whole site resource: `sku` (Free to Standard, which costs money and enables features the Free plan blocks, such as custom authentication and password protection settings in the configuration), `stagingEnvironmentPolicy`, `allowConfigFileUpdates`, repository settings. Only a template merged to `main` (owner-reviewed under the proposed CODEOWNERS) can do this, and each run re-applies `main.bicep` (Free), so it is self-healing. Recorded because the role description says "nothing else".
- Minimal fix: none needed now; keep the `sku` in `main.bicep` fixed by a rule test (`sku: { name: 'Free' ...}` or an allowed list), and consider an Azure Policy on the three groups that allows only the Free SKU.

### Info

- N-I1 (confirmed): **trust in the preview artifact**. The digest in the artifact name is computed by the pull request's own build, so for previews it proves integrity between upload and deploy, not origin; this is correct as designed. What is enforced instead: the zip digest recorded by GitHub (`site_artifact.py:170-172`, skipped if absent), the per-file digest, size limits, name checks, `open(..., "xb")` (no overwrite, no link creation), `chmod 0644`. The storage address is fetched without the GitHub token (`_NoRedirect` on API calls; `urlopen` for the signed URL). Error messages print names with `repr`, so a name cannot inject a workflow command.
- N-I2 (confirmed): **TOCTOU and races** in `preview-deploy`: `preview-target` and `fetch` both read the same run id; a completed run's artifacts cannot change without an Actions-write re-run, and a second artifact fails `fetch`. A pull request updated or closed between the check and the upload leaves a stale preview until the next prune; harmless. Two different pull requests can pass the three-slot check together (stated in `preview.sh:46-47`).
- N-I3 (confirmed): **`StaticSitesClient` check is detection after use** if the CLI ever downloads another build: `upload-site.sh:61-63` verifies the pinned file and the absence of other folders after `swa deploy` has run. The CLI is steered to the pinned file by `SWA_CLI_DEPLOY_BINARY_VERSION` and the pre-written `StaticSitesClient.json`, so a download needs Microsoft's metadata and CDN to change in a way that still matches the selected tag. Acceptable; a stricter variant runs the CLI with `HOME` pointing to a read-only copy.
- N-I4 (confirmed): **bootstrap re-runs apply whatever `main` holds**. README step 1 tells the owner to clone `main` in Cloud Shell and run `bootstrap.bicep` with Owner rights, and says re-running "changes nothing that already exists"; that is only true while the file is unchanged. A merged change to `infra/bootstrap/` (owner-reviewed) would run with subscription Owner rights. Advice: before every re-run, read `git log -p infra/bootstrap/` since the last run.
- N-I5 (confirmed): **CODEOWNERS** now covers `/infra/`, `/eng/deploy/`, `/.github/workflows/` for good. Not covered: `src/ThoughtTree.Client/wwwroot/staticwebapp.config.json` (the CSP of ADR-045) and `tests/secure/ThoughtTree.Architecture.Rules/Deployment/` (the rules that guard the pipeline). If, after the reviewer agent exists, any pull request outside the owner-only paths can merge without the owner, both the CSP and its rule can be weakened in one change. Consider adding both paths. The documentation changes (`AGENTS.md`, `architecture.md` section 7 and the decision row) match the code; the decision row records the owner's earlier choices as replaced "for the owner to confirm in the pull request", which is correct.

## 4. Settings the owner must verify (not visible to an agent)

1. Environments `test`, `production`, `preview`: deployment branches "Selected branches and tags" with exactly one rule of **type Branch** `main`; no tag rule, no wildcard. `production`: required reviewer `ProductOwnerRole`, Prevent self-review on, administrator bypass off. `AZURE_CLIENT_ID` set as an environment variable in each (and no repository variable `AZURE_CLIENT_ID`, so a missing environment value cannot fall back to another identity).
2. **Tag ruleset** (N-H1): only the owner may create, update or delete tags; at minimum block the tag names `main` and `refs/*`. Until N-H1 is fixed in code, before approving a production run, check that the shown commit is on `main` (`git branch -r --contains <sha>` shows `origin/main`) and that the `deploy-test` run's label is the branch `main`, not a tag.
3. Agent token of `AdventureDevelopment`: no Actions write (dispatch, re-run, delete artifacts), no Deployments write (approve), no Administration, Environments, Variables, Secrets write; also no permission to bypass rulesets.
4. Actions › General: fork pull request workflows need approval for all outside collaborators; default workflow permissions "Read repository contents"; "Allow GitHub Actions to create and approve pull requests" off; artifact and log retention at least 90 days if rollback should reach that far.
5. OIDC subject template default (`use_default: true`) for repository and organisation; repository name casing in the bootstrap parameter.
6. Branch protection or ruleset on `main` as decided 2026-11-17, including "Require review from Code Owners" and no administrator bypass; the CODEOWNERS entries of this branch take effect only after merge.
7. Azure: `az identity federated-credential list` for each identity in `rg-thoughttree-identity` shows exactly one subject `repo:AdventureDevelopment/ThoughtTree:environment:<name>`, issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`; `az role assignment list --all --assignee <principalId>` shows only "ThoughtTree site deployer" on the own site group; the old identities and Contributor assignments of an earlier bootstrap are gone (README step 0).
8. Azure: README step 6 (does one deployment token reach every environment of a site) and step 7 (no IP logs in a resource the owner controls).
9. Owner approval on record for the licences listed in N-L2 and for `StaticSitesClient`.

## 5. Not covered
